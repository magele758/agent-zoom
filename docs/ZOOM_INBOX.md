# OPC OS Zoom · 消息工作台

## 谁在用，打开它要做什么

你同时把工作交给不同 coding agent。打开 Zoom 时，第一个问题是「哪些任务需要我回答」。看完原问题、根据和选项，你可以当场给出决定，回到列表处理下一条。执行者随后在发起任务的上下文中取得答复。

| 你要做的事 | 页面需要提供什么 | 怎样算完成 |
| --- | --- | --- |
| 扫一眼今天要处理的事 | 所有已接入来源进入同一份消息列表，待你答复的事项容易找到。每条都写清来源、任务、时间和摘要 | 即便另一个 agent 又发了进度，之前的问题仍能在「待我处理」中找到 |
| 判断这条消息为什么来找我 | 点一行，在旁边读完整问题、同任务历史和已有证据。审批展示具体计划版本 | 可以回答「事情走到哪一步」和「接下来轮到谁」，无需切换终端 |
| 当场给决定 | 普通问题支持选项和文字。计划与最终验收使用各自的批准、要求修改和拒绝操作，失败或未知回执显示对应动作 | 答复带原问题或版本标识回到原任务，可在历史中核对。阅读、打开目录、归档都不代替批准 |
| 只看手里的一个项目 | 目录是工作主题，可以按「产品 / 子项目」组织。同一目录容纳多种 agent | 选择父目录包含其子目录，切回全部消息即可恢复跨项目视图 |
| 换一个 coding agent 继续使用 | 从原生会话用一个本机命令登记任务、报进展、提问、取回反馈。任务标识在重启和重试间稳定 | 两个来源使用相同的任务名或各自的内部编号时，问题和答案仍能准确配对 |

## 从总览走到具体事项

打开服务根地址或 `#overview` 进入全局看板。顶部保留跨产品的待答问题与审批，点击直接进入原消息。下方按项目列出十三个阶段。点「PageLens × 运维」只显示这个产品的运维事项，点「全部项目 × 运维」可跨产品查看。节点有独立地址，刷新和浏览器返回能找回该范围。手机先选项目，再点阶段。未标注阶段的历史任务保留单独入口。

「项目目录」登记长期维护的产品。先输入名称即可建项目，之后可把多个 GitHub 公开仓库归到同一目录。同步保存当时的开放 Issue、PR 数、最近事项、最新正式发布记录与来源链接。首次同步或仓库数据变化时，会有一条维护动态进入消息列表；仅重新核对时间会更新同步时间。需要你答复的任务继续进「待我处理」。

```sh
opc-os project add 新项目
opc-os project sync magele758/pagelens-agent --product PageLens
opc-os project sync magele758/pagelens-interpret --product PageLens
opc-os project list
```

同步在命令运行时读取 GitHub，页面展示最近一次本机快照与采集时间。开源维护按仓库事项和交付记录浏览；有经营数据的产品可以另外打开「渠道转化」。

## 消息列表的阅读顺序

1. **左栏选择范围。** 「全部消息」汇集各产品动态，「待我处理」汇集需要答复的原任务。目录树可以缩小范围。
2. **中栏选择消息。** 每个尚未答复的问题各占一行，其余任务显示最近一条动态。任务登记、逐条进展和往返答复保存在右栏历史。问题首句是列表标题，次要位置显示来源和时间。
3. **右栏理解并回应。** 展示所选事项的任务、目录、正文以及这件事实际允许的动作。相关历史留在当前任务内。窄屏先显示列表，选择后进入详情，再返回原列表。

目录描述工作归属，agent 名描述消息来源。例子是「OPC OS / 执行器」下 Grok 请求确认方案，Codex 随后提交差异，reviewer 提出返工。这些记录可以在一个目录里出现。目录栏采用深墨色，右侧按信件排版，用宋体标题和暖白纸色突出问题。朱红用于待决事项和发送动作。品牌图取自国际空间站拍摄的OPC OS山冰川，图片随应用本地加载。[影像来源与署名，NASA/JSC ISS045-E-53329](https://science.nasa.gov/earth/earth-observatory/glaciers-in-the-kunlun-mountains-northern-tibet-87104/)

## OPC-OS 如何组织产品

一个本机服务是一份共享数据。顶层目录表示长期经营的产品，子目录可以放模块、实验或专项。开发、测试、营销是对工作的分工，一个 coding agent 可以在不同环节提供证据。同一产品可以同时验证新想法、维护已发布版本、试两个获客渠道。首页始终把需要人的事项放在一起。

「产品进程」提供以下十三个阶段的索引。行数代表已登记任务，待处理数代表其中尚缺答复的问题或审批。一个阶段可以反复进入，登记阶段不会触发执行或认定该阶段已经达成。

| 顺序 | 环节 | 这一环节应该留下什么 |
| --- | --- | --- |
| 01 | 信息收集 | 访谈原话、工单、使用行为或竞品观察，注明来源和时间 |
| 02 | Idea | 哪类客户遇到什么问题，以及一次足以否定假设的小实验 |
| 03 | PRD | 场景、取舍、验收条件、上线后要验证的指标 |
| 04 | 设计稿 | 用户路径、界面版本及关键决策 |
| 05 | 开发组 | 有依赖的任务、负责人、差异与可复现检查 |
| 06 | 测试组 | 独立验证、回归证据、剩余风险与返工记录 |
| 07 | 发布 | 发出的版本、覆盖对象、决定人和回退位置 |
| 08 | 运维 | 故障、成本、使用状况和修复记录 |
| 09 | Trace | 用同一条记录串起来源、决定、执行和结果，复盘与预期的差异 |
| 10 | GTM | 首批目标客群、承诺、定价假设和渠道实验 |
| 11 | 营销推广、获客 | 哪个来源带来哪些客户，他们何时完成有价值的动作 |
| 12 | 营收 | 客户首单、复购及退款，用交易标识核实 |
| 13 | 记账 | 收款、退款、渠道和交付成本对应的凭证与对账差异 |

发布可以另设审批；哪些任务可并行由具体计划的依赖决定。Trace 在第九阶段集中复盘，来源与证据从信息收集时开始留存。GTM 可以在开发期间先验证渠道和定价。阶段中提到的材料是产品目标，当前界面提供任务分组与证据入口；自动发布、投放、财务入账仍需要各自的业务接入。

### 首个经营场景：获客渠道 → 激活 → 首单 → 复购

同一产品使用稳定的客户代号连接获客、激活事件和订单；日期、来源凭据、渠道和订单号伴随原始事件保存。不同产品的同名客户分别统计。录入真实数据前先定下这个产品的激活动作，例如协作工具可以选择「首次成功完成一次可交付任务」。选择什么动作要由产品目标决定。

渠道报告按客户首次获客来源归因。在获客人群中数后续激活的客户，在激活人群中数完成首单的客户，再在首单客户中数有第二个不同订单的人。每级同时展示人数和相邻转化率，分母为零时显示横线。保留原始事件供人核对；数据迟到时可以据时间重新计算。累计口径适合先打通链路，渠道效果比较还需要相同的观察窗口。

从侧栏打开「渠道转化」，选产品，点人数可核对客户代号、事件时间及来源。独立示例台账中，社群活动带来 2 位客户，两人都激活并下单，其中 1 位复购。点这格的 1 可以查到第二笔订单 `DEMO-1002`。点「未计入漏斗」可以查到另一笔订单 `DEMO-1099` 缺少获客记录的原因。示例库共 14 条事件，重复导入后计数相同。

各 agent 可用 `opc-os growth record events.json` 登记获授权的事件，用 `opc-os growth report 产品名` 读取同一地点的报告。可核对的客户代号、带时区的发生时间、来源及稳定的订单号是跨系统对账的基础。[事件格式与批量回执](../skills/zoom-inbox/SKILL.md#登记渠道转化记录)

建议增加三种回流方式。未激活的客户反馈回到信息收集或设计；已付费但迟迟不复购的客户回到产品与运营；归因到的收入在计入利润之前与退款、渠道费用和实际到账对账。后两项需要相应数据来源。关闭任务、发送推广或收到首单都不代表完成记账。

## 与现有 Herdr 流程的接缝

Grok 入口调用具名 workflow，设计人员先看仓库，隔离工作树按功能并行，独立人员读取差异做 review。agy 的主会话决定任务规模与能力分配，记录每个 worker 的窗口和目录，必要时把返修意见送回原会话。这两条路径都需要保留发起者、问题与执行现场的关联。

交给OPC OS调度的任务沿用版本审批、依赖、租约、证据与回执对账。已经在其他工具里执行的任务可以登记到列表并交流，执行权留在原处。原生会话需要接入上报和取回反馈的入口。尚未接入的独立终端无法自动出现在列表中。

消息列表标出谁需要答复，工作流详情展示执行阶段，共享的已读与归档由运行看板独立记录。参考了 Plannotator 同一版本的[状态设计](https://github.com/backnotprop/plannotator/blob/f61d44dc304ad15ce68cb71acace3abbf3346de0/adr/implementation/inbox-thread-state.md)、[状态存储](https://github.com/backnotprop/plannotator/blob/f61d44dc304ad15ce68cb71acace3abbf3346de0/packages/shared/inbox/store.ts)及[看板界面](https://github.com/backnotprop/plannotator/blob/f61d44dc304ad15ce68cb71acace3abbf3346de0/packages/inbox/board/BoardPage.tsx)。

## 在本机试用

使用 `npm run zoom:local` 打开持久的本机项目库。运行 `npm run zoom:preview` 则在新的临时 Git 仓库和 SQLite 中登记样例。打开打印的全局看板，先点待办里的 Grok 离线草稿问题，再选择「OPC OS」目录打开 Antigravity 的计划。计划可退回修改，也可批准后查看固定演示执行器的实现、独立复测和最终验收。预览中的每次答复仅写入这份示例库。

运行 `npm run test:zoom` 可重放桌面、手机的选择与回复。脚本还会验证原生 agent 按原问题取回答案、服务重启后继续读取，以及频道 agent 收到一次回复通知。桌面和手机截图输出到 `data/zoom-validation/`。
