# 一条启发怎样变成项目成果

从每日复盘走到发布，沿途留下的是同一个项目的材料、任务与决定。每个阶段都可以由任意能调用本地 CLI 的 coding agent 发起，也可以把工作委托给 Agent Home 的 Bot。阶段标明业务位置，实际派发顺序由任务依赖与计划审批决定。[设计导读](../OPC_OS_PRODUCT_INTENT.md) · [业务流程图](flows.html#business)

<a id="work-flow"></a>

## 一个 PageLens 例子

11 月 20 日的日记确有「自建工作流评测模板」条目。下面的 PageLens 特性、发布与反馈是用来讨论产品的情境。（日记原文件位于 `$OPC_DAILY_REVIEW_DIR/2026-11-20.md`。）

1. **记启发，选项目。** 读完条目，你想到「PageLens 能否用固定样例重放字段检查失败？」可以选已有的「发布前检查」项目，新建验证项目，或先留在想法里。材料随想法保存。
2. **研究后再定范围。** 在项目 room 点名研究 Bot，或请 coding agent 对照原 Issue 和其他项目的夹具，重放一次失败操作。研究者交回样例、限制和证据。你可以留存结论，也可以把它转成特性。
3. **把交付交出去。** 发起者提交计划，你确认具体版本。OPC OS派发，Herdr 承载实现与独立评审。需要判断「哪些字段缺失要阻止提交」时，问题进入 Zoom，你的答复回到原问题。评审失败退回实现者，复测通过后进入最终验收，获得发布授权才上线。
4. **让真实结果回到原想法。** 发布记录附版本、验证结果和回退位置。报告者用新版复测后，证据回到原 Issue 和项目。尚未收到回复就显示「等待用户复测」。另一个产品引用这版夹具时，记录自己的验证。回看最初的想法，可以查到两个项目各自的结果。

## 每阶段交什么，拿什么验收

| 阶段 | 可以交给 agent 的工作 | 验收依据 |
| --- | --- | --- |
| 公司 · 信息收集 | 核实日记中的一条线索 | 日记位置、原始来源 |
| 公司 · 想法 | 找相似尝试，提出一次最小验证 | 引用材料、假设、目标产品 |
| 项目 · PRD | 写清谁在什么场景遇到什么问题 | 范围、PRD 版本、验收样例 |
| 设计稿 | 画出关键操作及异常后的恢复路径 | 原型、待决定的交互取舍 |
| 开发组 | 按能力分工，在各自会话实现 | 代码差异、自测结果、关联任务 |
| 测试组 | 独立复测，退回并复查失败用例 | 复现步骤、测试输出、评审决定 |
| 发布 | 核对变更、回退步骤与授权 | 候选版本、放行决定、实际发布凭据 |
| 运维 | 从仓库或服务发现问题并处置 | Issue、PR、日志、告警及负责人 |
| Trace | 沿一次失败追到运行、版本和决定 | 时间线、证据缺口与改进项 |
| GTM | 验证目标人群、使用场景或价格 | 访谈记录、实验结果及适用范围 |
| 营销推广、获客 | 按渠道比较同一观察期内的使用 | 渠道来源、该产品的激活动作、转化记录 |
| 营收 | 核对首单、复购与退款 | 订单、支付或退款凭据、差异 |
| 记账 | 将收款、退款、渠道成本与凭证配对 | 对账明细、待确认的入账草稿 |

## 发布以后怎样决定下一轮

开源维护可以通过原 Issue 的复测、真实使用反馈或跨项目采用来验收。商业产品则跟踪获客渠道、激活、首单与复购，核对订单、退款、渠道成本和已知投入。项目复盘写明观察对象、时间和版本。数据只能归到产品时，保留其实际归属。对外发布与停服分别取得授权。

Bot 整理证据，需要取舍时由 Zoom 送来「继续投入、调整方向、暂停观察」。决定及理由回到项目和原想法。新提案可接续历史，经验可选入日常库的专题。公司统一的营收和成本口径留待接入真实资料时确定。

当前渠道报表已能从产品和渠道下钻到事件来源。事件记录客户与订单标识，发布版本归属、金额、成本和退款仍需接入，完整的经营复盘属于设计目标。[渠道转化页面](../../web/src/GrowthReport.tsx) · [当前事件字段](../../src/growth-types.ts)
